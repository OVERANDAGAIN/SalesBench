## 3. 已确认需求与技术方案

以下均为本轮用户已确认决定，不是从演示代码推导的正式需求。

- SalesBench 是包含多个竞争商家、真人或 Agent 买家、交流和购买行为的实验平台，不按普通电商网站定位。
- 买方整体界面及主要交互已认可，后续迁移应保留，不重新设计。
- 一级页面顺序固定为：**排行榜、商品推荐、公共交流、私聊、我的**。
- 排行榜面向市场参与者展示商家竞争情况；商品推荐用于浏览商品；公共交流采用“商家描述 + 多人发言 + 商家公开回复”，不做视频流；私聊用于定向交流；“我的”显示个人及购买相关信息。
- 商品详情和购买确认使用二级页面或弹窗，不增加无关一级页面。
- Agent Buyer 提供模型可用的结构化观察、动作与执行回执，不建设 Agent 管理 UI。Seller 界面未来扩展，本轮不建设。
- 技术方案已确定：**Vue 3 + TypeScript + Vite；FastAPI；PostgreSQL + SQLAlchemy + Alembic；独立 Python 实验内核**。
- 后续使用一个 SalesBench 总仓库，统一管理前端、平台后端、Python 主体和消费者模型，内部按职责分目录。实际仓库和本地总工程位置在接管阶段确认，本轮未建立。
- Python 主体与消费者模型由其他任务建设。界面认可不表示原型中的模拟排名、推荐、回复和交易成为正式实验规则。

当前收到的是原生 HTML/CSS/JavaScript 原型，尚不是上述技术栈的实现。

## 5. 当前状态、消息和购买处理

### 5.1 状态生命周期（代码事实）

`createSalesBench()` 的闭包保存 `merchants`、`products`、`buyers`、`publicMessages`、`privateMessages`、`revision`、`sequence`、`receipts` 和 `listeners`（`core.js:15–41`）。`app.js:3–5` 只建立一个实例，并固定绑定 `buyer_001`。

五页、真人按钮和 `window.salesbench` 使用同一个 `buyer`。公开消息按商家保存；私聊按“买家 → 商家”保存；余额、订单及浏览状态在各自买家对象中。`buyer_002` 是内核测试用的第二个身份，界面不提供身份切换。不存在跨浏览器真实多用户会话。

状态仅在当前页面内存中，不使用数据库、localStorage、sessionStorage 或 IndexedDB；刷新、重开均重新初始化，不同标签页互不共享。`app.js:13` 另外保存 `dialogState`、计数器、提示计时器和 `draft`；聊天草稿按“view:merchantId”区分，也不持久化。

### 5.2 消息处理（代码事实）

表单提交由 `app.js:46` 转为 `send_public` 或 `send_private`。`core.js:89–102` 验证商家及去空白后 1–500 字消息，写入相应内存数组，并立即追加商家预设回复：优惠类、价格类关键词分支，其余使用商家固定文本。

消息含标识、作者、角色、文本、时间和 `preset` 标记；买家新发消息带 `authorId`。`messageHTML()` 渲染气泡及演示标签，`render()` 滚动到消息末尾。公开区的“多人”主要由种子消息体现；不是已接入的实时多人或模型对话。

### 5.3 购买处理（代码事实）

真人路径为商品卡 / 详情 → `checkout()` → 确认按钮 → `buyer.execute({ type: 'purchase', ... })` → `purchased()` → 继续浏览或我的。打开确认框本身执行的是 `view_product`，不扣款。

确认框保存 `actionId` 和当时单价，预检数量、库存及余额。真正状态更新在 `core.js:103–113`：校验商品、1–99 整数数量、`expectedUnitPriceCents`、库存和余额；成功后在当前同步调用内扣余额、减库存、加商家模拟成交额与件数、插入本人订单，并记录 `lastDecision`。金额以整数分保存，显示时换算为元。

`decline_purchase`（`:86–88`）清除详情聚焦并记录不购买决定，不产生订单或扣款；`browse` 和 `close_detail` 也没有购买扣款逻辑。“继续浏览 / 关闭”和“明确暂不购买”不是同一个动作。

这只是本地同步模拟更新，不能视为数据库事务、真实支付或并发交易已经实现。

## 6. 观察、动作、回执与通知在哪里

本节描述当前接口，**不是下一阶段最终 API 协议**。这些是内存方法，不是 FastAPI 路由。

### 6.1 观察

`createSalesBench().bindBuyer(buyerId)`（`core.js:48`）返回绑定身份的对象，含 `observe()`、`execute()`、`subscribe()`。`observe(query)` 在 `:51–64`：

- query 仅接收 `view`、`merchantId`、`productId`；不能用额外 `buyerId` 等字段切换身份。
- view 支持 `leaderboard / products / public / private / me / product`。`product` 是详情观察，不是第六个一级页。观察指定 view 本身不改变当前导航。
- 成功观察包含 `schemaVersion`、`revision`、`actor`、`navigation`、`demoConfig`、商家公开描述和 `permissions`；按 view 增加榜单、商品、消息、本人订单等字段。
- `productView()`（`:44`）和 `merchantView()`（`:45`）组织公开字段，`rank()`（`:47`）补充排名与模拟销售指标。`private` 仅读取当前买家的所选会话，`me` 返回本人订单。
- 使用 JSON 克隆返回结果；未提供整体 `getState()` 导出。测试种子中的 `merchantInternal` 成本（`:39`）没有被加入观察输出。

本地可见性约束存在于上述接口中；源码、种子和内核构造函数仍在浏览器端，不能当作生产认证或可信隐私隔离。

### 6.2 动作与回执

`execute(input)` 在 `core.js:65–120`，动作字段白名单在 `:71`。输入顶层仅允许 `id / type / payload`。

| 动作 | 当前 payload | 当前含义 |
|---|---|---|
| `browse` | `page`，可选 `merchantId` | 切换五页之一或按商家浏览 |
| `view_product` | `productId` | 记录详情聚焦；浏览器适配器另负责打开弹窗 |
| `close_detail` | 空对象 | 清除详情聚焦 |
| `send_public` / `send_private` | `merchantId`、`text` | 写消息并同步追加预设商家回复 |
| `purchase` | `productId`、`quantity`、`expectedUnitPriceCents` | 立即执行模拟购买；不是请求展示确认框 |
| `decline_purchase` | `productId` | 记录暂不购买 |

成功回执在 `:115–119` 生成，含 `ok / schemaVersion / actionId / actorId / type / revision / replayed / result`。失败由 `fail()`（`:66`）返回 `error.code` 和 `error.message`，例如数量非法、错价、缺货、余额不足。

`receipts` 以内存中的 `buyerId:actionId` 为键，仅缓存成功回执（`:68–69、117`）。重放判断比较 `JSON.stringify(input)`；序列化一致时返回原回执并标记 `replayed:true`，不重新执行；同编号且序列化不同返回 `ACTION_ID_CONFLICT`。这不是跨进程、跨重启的持久幂等能力，也不应扩大解释为任意 JSON 字段顺序下的语义等价。

每次新成功动作都会增加 `revision`，包括浏览等非购买动作；失败和命中缓存的重放不走该递增路径。它目前是实例内计数，不是正式实验轮次或数据库版本。

### 6.3 浏览器 Agent 接口

`app.js:51–52` 的冻结 `agentAPI` 经 `Object.defineProperty` 暴露为 `window.salesbench.observe(query)` / `window.salesbench.execute(action)`，固定使用当前买家，不暴露 `bindBuyer` 或整个市场对象。

执行成功后适配器会更新弹窗：`view_product` 调用 `openDetail(..., false)` 避免再次发动作；`purchase` 展示完成弹窗；其余成功动作关闭弹窗。Agent `purchase` **直接完成模拟交易**，不经过真人确认按钮。该语义是当前演示事实，正式执行权限及确认策略仍需后续确定。

`app.js:53` 检测 `document.modelContext?.registerTool`，尝试注册 `salesbench_observe` 和 `salesbench_execute_action`，注册错误被捕获。代码存在不代表注册成功；原交付明确说 WebMCP 未验证，本轮也未验证。它不是阶段 2 必须依赖的已验证能力。

### 6.4 状态通知与界面提示

`core.js:121` 的 `subscribe(listener)` 将回调加入同一实例的 `listeners`，返回取消订阅函数。新成功动作在 `:118` 同步调用监听器，无事件参数；监听器需要再次观察状态。失败及缓存重放不会触发这一段通知。

`app.js:49` 使用 `buyer.subscribe(render)` 让共享状态变化反映到界面。该订阅未暴露在 `window.salesbench` 的两个方法中，也不是 WebSocket、SSE、消息队列或操作系统通知。`toast()`（`app.js:19`）、表单错误和完成弹窗属于界面反馈，需与执行回执区分。
